# 设计说明

## 1. 为什么做这个

复习和读论文时最耗时的不是「读」，而是三件收尾的脏活：

1. **定位**：记得看过，但说不清在哪一篇哪一段；关键词搜不到同义表达。
2. **核对**：通用大模型的答案和自己的教材口径不一致，无法判断该信谁。
3. **回访**：当时卡住的概念，不进任何清单，下次复习从第一页重来。

常见做法各有缺口：笔记软件有全文搜索但没有语义召回，也不记录「哪里没懂」；RAG 聊天机器人能答但答案不可核对，且每次对话都是新开始；间隔重复软件（Anki）需要手工制卡，录入成本高到大多数人坚持不下来。

拾卷的取舍是：**把「检索」和「记忆」都做成可查的数据**，答案只从资料里抽取，不自由生成；「没懂」由系统自动判断（资料没讲到）或一键标记，不要求用户制卡。

## 2. 三个关键决策

### 2.1 答案为什么是抽取式，而不是生成式

生成式答案读起来更顺，但带来两个问题：需要模型 Key（评审复现成本高），以及答案不可核对（与赛题「技术作用可核对」的要求相冲突）。

因此答案由三部分组成：

1. **段落候选**：把每个命中片段按空行切成段落，标题丢弃，以冒号结尾的引导句与后面的列表合并（否则「处理流程分五步：」会丢失五步）。
2. **打分**：对查询做中文 2-gram 切分，按「查询词 × 稀有度」加权——`weight = log(1 + 段落总数 / (1 + 包含该词的段落数))`，再乘以检索名次权重与长段落惩罚。常见词（如「什么」）权重接近 0，能区分答案的词（如「缺页」）权重高。
3. **选取**：要求命中 ≥2 个查询词，与已选段落重合度低于 0.45，第二条引用必须与第一条同源，避免答案跨文档拼贴。

代价是表达生硬、长段落会被截断；换来的是每句话都能点回原文，且完全离线。

### 2.2 「资料没讲到」怎么判断

最初用向量相似度阈值，实测发现 bge 的 cosine 相似度整体偏高：问「React 的 useEffect」时，最相近的片段相似度仍有 0.97，与真正命中的 0.9716 几乎无法区分。原因是中文短查询与任意中文段落在同一语义空间里都偏近。

因此改为**查询词覆盖率**：查询的 2-gram 有多大比例出现在命中片段里，低于 34% 判定为「没讲到」。这个指标可解释、可复现，也不依赖模型校准。相似度仍然展示（`cos` 字段），但只作参考。

### 2.3 记忆为什么放 seekdb 而不是浏览器

需求是「换会话、换浏览器还在」。localStorage 只能跨标签页，做不到。记忆天然是结构化数据：按学习者查、按状态过滤、按次数排序，正好是 SQL 的强项；而文档检索需要向量与全文索引，正好是 seekdb 的强项。两者放同一个库，事务上还能保证「提问记录」和「薄弱点」一起成功。

## 3. 数据模型

```
sj_collections   资料集登记：slug(主键) / label(中文名) / created_at
                 集合名只允许 [a-zA-Z0-9_]，中文名通过 sha256 前 10 位生成 slug

sj_learners      学习者：id / name / created_at / last_seen

sj_questions     提问流水：learner / collection / question / mode / top_score / hit_count / created_at
                 top_score 存的是查询词覆盖率，用于统计「平均覆盖」

sj_weakpoints    薄弱点：learner + collection + concept 唯一
                 asks 累加提问次数，misses 累加「没懂」次数，status ∈ {open, mastered}
                 last_score 记录最近一次覆盖率，evidence 存当时最接近的片段

sj_reviews       复习流水：weak_id / result ∈ {understood, still_lost} / created_at
```

`concept` 由问题归一化而来：去掉标点与「请问 / 帮我看看」等前缀，截断到 40 字。同一概念反复提问只累加计数，不会刷屏。

## 4. 检索链路

```
查询
 ├─ 本地 bge 向量化（带 bge 官方查询指令前缀）
 ├─ seekdb hybridSearch：全文(ngram2) + KNN(HNSW) 双路召回，各取 40 条
 │    └─ RRF(k=60) 在库内融合，返回 Top-K
 └─ 客户端只拿到排序结果，不做任何两路合并
```

混合检索的意义在于互补：查「换页时硬盘做什么」这种口语化问题，向量路能命中「缺页中断」段；查「ngram2」这种术语，全文路更准。RRF 只看名次不看分数，避免两种分数量纲不一致的问题。

## 5. 交互流程

```
导入：粘贴/选文件 → 切片 → 批量向量化 → upsert → refresh_index → 用最后一片自检
提问：检索 → 覆盖率判定 → 抽取答案 → 记 sj_questions → 未覆盖则写 sj_weakpoints
复习：列出 open 的薄弱点 → 懂了(mastered) / 还是不懂(计数+1) → 记录 sj_reviews
```

导入自检是一个刻意设计：写入后立刻用新片段的正文去检索，命中才算导入成功。因为 seekdb 的向量索引需要 `refresh_index()` 才对新增数据生效，漏掉这一步会出现「导入成功但搜不到」的假成功。

## 6. 没做什么

| 没做 | 原因 |
|---|---|
| 大模型生成答案 | 需要 Key，且答案不可核对；与「可复现、可验证」冲突 |
| PowerContext 接入 | 赛题要求 seekdb / PowerContext 二选一；本机已有 seekdb 实例，选它能让「记忆」也落在同一个库里 |
| 用户登录与多租户 | 单机自用定位，`learner` 字段足够演示跨会话复用；加鉴权会拉长评审复现路径 |
| PDF / 图片解析 | 让评审用最少的依赖跑通优先，纯文本已经能证明链路 |
| 前端框架 | 单页 + 原生 ES Module，零构建，`npm start` 即用 |
