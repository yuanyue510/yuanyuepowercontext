## 三、导入顺序

只有一份 DSL，无先后依赖：

1. 起 seekdb，执行 `bridge/sql/01-schema.sql`、`02-seed.sql`
2. 起 `bridge` 服务，`curl http://<宿主机IP>:5000/health` 应返回 `{"ok":true,...}`
3. 起 Dify
4. 在 Dify 配置模型供应商（OpenAI 兼容，填 `base_url` / 模型名 / API Key）
5. **先改 DSL**：把 `dsl/grudge-tavern.yml` 里 `查账本`（约 215 行）、`落账`（约 408 行）两个 HTTP 节点的 `http://192.168.192.128:5000` 换成你的宿主机 IP
6. 导入 DSL → 发布 → 打开应用，名号填「张三」开始

## 四、凭据说明

本包内**不含任何真实凭据**。`dsl/grudge-tavern.yml` 中的模型名为占位值，导入后需在 Dify 里重新绑定你实际的模型服务（README §4.4 有字段对照表）。`bridge/docker-compose.yml` 中 `SEEKDB_PASSWORD`、`POWERCONTEXT_TOKEN` 均为空字符串，按你的环境填写。

## 五、当前限制（如实说明）

| 项 | 状态 |
|---|---|
| 模型 | 交付时验证用的是 `verification/mock_llm.py` 这个规则假模型：链路、落库、跨会话记忆全部真实，但**台词是规则拼接的，不是真模型生成**。接入真实模型后体验会明显不同 |
| WebApp 入口 | 本套 Dify 1.9.1 自建部署中 `/chat/<APP_ID>` 的登录接口 404，截图改从 Studio 的 Preview 面板完成。API 方式（`POST /v1/chat-messages`）正常 |
| 网络 | DSL 中的地址是内网 IP，评审复现需按第 6 步替换 |
| 检索方式 | `lore` 的设定检索用的是关键词匹配，未使用向量检索。seekdb 承担的是应用数据存储职责 |
